# Участие в разработке Solana Yellowstone gRPC Data Core

[← Главная](../README.md) · [🇬🇧 English](../CONTRIBUTING.md) · [🇷🇺 Русский](CONTRIBUTING.ru.md) · [Архитектура](ARCHITECTURE.md) · [Правила общения](../CODE_OF_CONDUCT.md)

Это экспериментальная Go-библиотека. Изменения должны сопровождаться понятным объяснением поведения, проверками и границами гарантий.

## Как предложить изменение

1. Изучи [архитектуру и инварианты](ARCHITECTURE.md), а также [технический долг](TECH_DEBT.md). Определи, относится ли функциональность к универсальному ядру или к прикладному обработчику.
2. Для нетривиальной ошибки или новой функции открой [Issue](https://github.com/sirdont0/solana-yellowstone-grpc-data-core/issues/new/choose) с воспроизведением и ожидаемым поведением.
3. Создай отдельную ветку от `main`, избегай несвязанных рефакторингов и добавь содержательные тесты.
4. Оформи PR по [шаблону](../.github/PULL_REQUEST_TEMPLATE.md), указав изменения, проверки и оставшиеся ограничения.

Если репозиторий ещё приватный, для участия нужен доступ к нему. Действуют [правила общения](../CODE_OF_CONDUCT.md).

## Локальная проверка

Нужен Go 1.26.11+. Обычные unit-тесты запускаются без реального Yellowstone-провайдера:

```bash
go test -count=1 ./...
go test -race ./...
go vet ./...
git diff --check
```

Форматируй изменённые Go-файлы через `gofmt`. При изменении protobuf запускай [скрипт генерации](../scripts/regenerate-proto.sh), проверяй diff и совместимость с protobuf-клиентом Aggregator V2.

## Требования к корректности

- Наблюдение источника нельзя автоматически считать полным каноническим состоянием, даже при `finalized`, reconnect или наличии WAL.
- `bank_id` и `write_version` конкретного источника нельзя напрямую сопоставлять между разными backend-валидаторами.
- Сохраняй воспроизводимость по WAL каждого источника и явно отмечай разрывы/неопределённость.
- Учитывай ограниченные очереди, отмену, ошибки записи и обратное давление; потеря данных не должна скрываться.
- Экономика протоколов и торговая логика живут вне ядра. Для новых программ реализуй `Handler` и явно отклоняй неизвестные форматы.
- Проверяй реальные аварийные сценарии: некорректные данные, конфликтующие дубликаты, переподключение, повреждённый WAL, позиции CPI.

## Секреты и ревью

Не добавляй токены провайдеров, приватные ключи, `.env`, рабочие WAL и чувствительные фикстуры в Git. Очищай логи и примеры перед публикацией. Уязвимости сообщай по [SECURITY.md](../SECURITY.md).

В PR укажи затронутые пакеты, влияние на совместимость, доказательства корректности и известные ограничения. Тесты нужны для изменений поведения; изменения документации можно проверить вручную.
